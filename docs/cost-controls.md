# USED 공개 운영 비용 제어

로그인 없이 검색·상세를 이용하되, Vercel Hobby 무료 요금제를 유지한다. 신규 유료 데이터베이스, 유료 API, Marketplace 통합, 유료 애드온은 추가하지 않는다. 무료 사용량을 다 쓰면 기능이 중단될 수 있으며, 서비스를 계속 운영하기 위해 자동으로 유료 플랜으로 전환하지 않는다.

비용 제어는 두 층으로 나뉜다. **과금 방지는 현재 Hobby 요금제의 무료 사용 한도에 의존**하고, 아래 애플리케이션 장치는 한도 소진과 원문 서비스 과부하를 늦춘다. 메모리 카운터만으로 전체 배포의 사용량이나 비용을 보장하지 않는다.

현재 팀의 Hobby 플랜은 실제 연결 정보로 확인했다. Vercel은 Hobby를 무료 플랜으로 설명하며, 대부분의 한도를 초과하면 30일이 지나야 해당 기능을 다시 사용할 수 있다고 안내한다. [Hobby 요금제 공식 문서](https://vercel.com/docs/plans/hobby)

## 검색 범위와 화면 동작

| 진입 시 선택 | 검색할 수 있는 서비스 |
| --- | --- |
| 중고물품 | 당근, 중고나라, 번개장터, 헬로마켓 |
| 중고차 | 엔카, KB차차차, K Car |

홈에서 선택한 종류는 검색 결과에 들어간 뒤에도 유지한다. 결과 화면에서 검색어를 바꾸어도 다른 종류의 서비스를 함께 조회하지 않는다. 종류를 바꾸려면 홈으로 돌아가 선택한다. 결과 화면의 종류 탭과 서비스 탭은 제거하고, 서비스 선택은 필터 안에 둔다. 필터의 `전체`도 현재 종류에 포함된 서비스만 뜻한다.

가격, 지역·내 주변, 반경, 정렬, 상품 상태, 연료·연식 등의 조건은 필터 시트에서 한 번에 적용한다. **검색 서비스가 같다면 이 조건을 바꾸어도 검색 API를 다시 호출하지 않는다.** 이미 가져온 목록에서 필터와 정렬을 수행한다. 검색 서비스 자체가 바뀌면 선택한 서비스에 한해 검색하며, 같은 검색이 캐시에 있으면 이를 재사용한다.

이 방식의 한계도 있다. 원문 서비스의 모든 결과에 필터를 적용한 전체 검색이 아니라, 현재 가져온 일부 결과를 필터링한다. 조건에 필요한 가격·지역·좌표가 없는 매물은 해당 조건에서 제외될 수 있다. 현재 위치 좌표는 외부 검색 API에 전송하지 않는다.

## 서버 요청 제어

구현 위치는 `server/cost-guard.mjs`, `server/handler.mjs`, `server/detail-handler.mjs`, `server/providers/`다.

| 항목 | 검색 API | 차량 상세 API |
| --- | --- | --- |
| 경로 | `/api/search` | `/api/detail` |
| IP별 요청 한도 | 60초에 12회 | 60초에 40회 |
| 동시에 처리하는 서로 다른 조회 | 2개 | 4개 |
| 성공 응답 메모리 캐시 TTL | 180초 | 600초 |
| 캐시 항목 수 상한 | 64개 | 96개 |
| 캐시 전체 직렬화 크기 상한 | 4 MiB | 4 MiB |
| 캐시 항목 하나의 크기 상한 | 512 KiB | 512 KiB |
| IP 카운터 수 상한 | 2,048개 | 2,048개 |
| 외부 조회 시간 제한 | 전체 18초 | 전체 10초 |
| Vercel 함수 실행 시간 상한 | 25초 | 15초 |

이 수치는 **각 함수 인스턴스 안의 해당 핸들러 기준**이다. 인스턴스가 여러 개 생기면 처리량이 합산되고, 콜드 스타트나 재배포 시 카운터가 초기화된다. 검색과 상세의 카운터·동시 처리 한도도 서로 분리되어 있다. 전체 서비스 일일 호출 한도, 사용자별 영구 할당량, 익명 세션별 할당량은 구현하지 않았다.

Vercel 환경에서는 신뢰할 수 있는 프록시가 설정하는 `x-real-ip`의 IP 형식을 검증해 카운터 키로 쓴다. 임의의 `x-forwarded-for`, 사용자 ID, 쿠키로 제한을 초기화하지 않는다. 유효한 IP가 없으면 공통 `unknown` 버킷을 쓴다. 로컬 개발에서는 공통 `local` 버킷을 쓴다. 같은 네트워크의 여러 이용자는 한도를 공유할 수 있다.

요청 처리는 다음 순서다.

1. HTTP 메서드, 검색어·서비스·차량 ID와 허용된 파라미터를 검증한다.
2. API 중단 정책과 IP 한도를 확인한다.
3. 같은 의미의 검색 또는 동일 차량의 성공 응답이 캐시에 있으면 반환한다.
4. 동일 키의 조회가 진행 중이면 그 작업을 기다려 중복 외부 요청을 만들지 않는다.
5. 새로운 조회의 동시 처리 한도가 찼으면 대기열을 늘리지 않고 일시 제한 응답을 반환한다.
6. 허용된 조회만 원문 서비스로 전달하고, 성공 응답만 캐시에 저장한다.

검색어는 Unicode NFKC 정규화, 앞뒤 공백 제거, 연속 공백 통합 후 키로 사용한다. 검색 키에는 종류·서비스·검색어가 모두 포함된다. 차량 상세 키에는 서비스와 매물 ID가 포함된다. 알 수 없는 파라미터와 중복 파라미터는 거부하므로 임의의 `timestamp`를 붙여 외부 조회를 계속 새로 만들 수 없다.

IP 카운터 저장소가 가득 차면 기존 활성 카운터를 지워 새 요청을 받아들이지 않는다. 새 식별자에 `API_BUSY`를 반환한다. 캐시가 가득 차면 오래된 항목부터 제거한다. 캐시 크기 상한은 직렬화한 데이터 기준이며 JavaScript 객체 등의 전체 메모리 사용량 상한은 아니다.

중복 조회를 기다리는 이용자도 IP 요청 횟수에는 포함된다. 함수까지 도달한 메모리 캐시 적중 요청도 포함된다. 반면 CDN이나 브라우저 캐시에서 응답한 요청은 이 함수 카운터를 거치지 않는다.

## 원문 서비스 보호와 엔카 복구

서버의 제공사별 가드는 각 서비스에 동시에 2개의 작업만 허용한다. 원문에서 HTTP 403·407·429가 발생하면 해당 인스턴스에서 그 제공사의 서버 조회를 5분간 쉰다. 이 한도 역시 여러 함수 인스턴스와 검색·상세 핸들러를 합친 전역 한도는 아니다.

검색에서 `전체`를 선택하면 일반 중고는 최대 4곳, 자동차는 최대 3곳으로 조회가 확장된다. 목록의 `limit: 30`은 제공사별 요청 값이며 전체 합계 한도가 아니다. 제공사 내부에서 여러 원문 요청이 필요할 수도 있으므로 검색 한 번을 외부 HTTP 요청 한 번으로 계산하지 않는다.

엔카 검색에는 서버 환경의 접근 제한을 보완하기 위한 기존 브라우저 CORS 조회가 있다. 서버가 정상적인 검색 응답 형식으로 엔카 실패 또는 엔카 제공사의 대기 상태를 알려 준 경우에만 브라우저에서 한 번 복구를 시도한다. 이 브라우저 조회가 실패하면 같은 탭에서 5분 동안 추가 복구를 쉬도록 한다. 서버 전체의 429·503, `API_BUSY`, `API_DISABLED`, 제공사 `PROVIDER_BUSY`에는 복구하지 않는다. 다른 종류나 다른 서비스를 선택했다면 엔카 복구도 실행하지 않는다.

차량 상세도 동일 서비스·동일 매물 ID를 명시한 엔카 원문 실패 또는 `PROVIDER_COOLDOWN` 응답에 한해 브라우저 CORS 조회를 한 번 시도한다. 브라우저 조회가 실패하면 같은 탭에서 5분간 추가 복구를 쉰다. API의 429, `API_BUSY`, `API_DISABLED`, 제공사 `PROVIDER_BUSY` 및 위의 명시적인 엔카 복구 계약을 만족하지 않는 503에는 복구하지 않는다. HTML 로그인 페이지나 알 수 없는 JSON도 복구 근거로 사용하지 않는다.

브라우저가 원문으로 직접 보내는 복구 요청은 Vercel 서버의 IP 카운터나 제공사 동시 처리 한도에 포함되지 않는다. 따라서 서버 제어만으로 원문 서비스의 전체 요청량이 제한된다고 설명해서는 안 된다.

## 캐시와 정보 신선도

| 계층 | 검색 | 차량 상세 |
| --- | --- | --- |
| 브라우저 탭 메모리 | 16개, 180초 | 12개, 600초 |
| 서버 인스턴스 메모리 | 64개·4 MiB, 180초 | 96개·4 MiB, 600초 |
| CDN 응답 정책 | `s-maxage=180` | `s-maxage=600` |

브라우저 검색 캐시는 종류·서비스·정규화한 검색어를 구분한다. 상세 캐시는 API origin·서비스·매물 ID를 구분하고, 저장한 응답을 꺼낼 때도 선택한 매물의 원문 URL과 ID를 재검증한다. 오류·취소·형식 불일치 응답은 성공 데이터로 보관하지 않는다. 일부 제공사만 성공한 검색은 성공한 결과와 제공사 상태를 함께 캐시할 수 있다.

탭 메모리는 뒤로가기 후 동일 결과·상세를 다시 열 때 API 호출을 줄이며, 브라우저를 다시 시작하면 유지되지 않는다. 검색 기록이나 상세 응답을 서버 데이터베이스에 영구 저장하지 않는다. 찜 데이터는 별도 기능으로 브라우저에 저장된다.

각 TTL은 해당 계층에 저장한 시각부터 계산한다. 서버·CDN·탭 캐시의 TTL이 겹칠 수 있으므로 **표시 정보가 항상 최근 3분 또는 10분 이내라는 보장은 아니다.** 매물의 확인 시각을 표시하고, 판매 여부·최종 가격은 원문에서 확인한다. 재시도 버튼은 브라우저 검색 캐시를 건너뛸 수 있지만 서버·CDN 캐시까지 무조건 무효화하는 기능은 아니다.

## 제한 응답과 사용자 경험

검색 API에 실제로 도달한 해당 IP·인스턴스의 60초 요청 구간을 기준으로, 12회 중 10번째부터 80% 사전 안내를 제공한다. 이 값은 서비스 전체 무료 사용량이나 개인의 월간 할당량이 아니다. 12번째 검색까지 허용하며, 다음 요청이 429로 거절되면 `Retry-After`에 맞춰 대기 시간을 보여 준다.

경고는 검색 결과 위의 작은 배너로 표시하고 같은 구간에서 닫은 경고는 다시 띄우지 않는다. 제한 시 같은 종류·서비스 범위의 마지막 성공 결과를 유지하며 이전 검색어를 제목에 명시한다. 새 검색어의 결과로 오인하지 않도록 기존 검색어로 목록을 필터링한다. 다른 종류·서비스의 결과를 대신 표시하지 않는다. 대기 중에도 찜·원문 링크·기존 결과 필터와 이미 저장된 검색 캐시는 사용할 수 있다. 시간이 지나면 안내만 해제하고 자동 재검색하지 않는다.

호출자별 `rateLimit` 안내는 서버 메모리 캐시와 진행 중 공유 작업의 바깥에서 생성한다. 안내를 담은 응답은 `Cache-Control: private, no-store`, `CDN-Cache-Control: no-store`, `Vercel-CDN-Cache-Control: no-store`로 다른 이용자에게 캐시되지 않게 한다. 80% 미만의 일반 응답에는 사용량 메타데이터를 넣지 않고 기존 CDN 캐시를 유지한다. 브라우저 검색 캐시에도 이 메타데이터를 저장하지 않는다. 별도 사용량 조회 API나 주기적인 네트워크 확인은 추가하지 않는다.

CDN 캐시에서 바로 응답한 검색은 서버의 요청 카운터를 거치지 않는다. 인스턴스가 바뀌거나 같은 IP를 여러 사람이 공유하면 계측 범위도 달라지므로 화면에 정확한 개인 잔여 횟수나 서비스 전체 사용률을 표시하지 않는다. 배너의 초 단위 갱신은 로컬 타이머로만 처리한다.

IP 한도 초과는 HTTP 429와 `API_RATE_LIMIT`, 동시 처리 한도 초과는 HTTP 503과 `API_BUSY`를 반환한다. 중단은 HTTP 503과 `API_DISABLED`를 반환한다. 제한 응답에는 `Retry-After`를 포함하고 `Cache-Control: no-store`를 사용한다. 화면에는 잠시 후 다시 시도하거나 원문을 확인하도록 안내한다.

브라우저는 입력하는 글자마다 실시간 검색하지 않고 검색 제출 시 조회한다. 진행 중인 동일 검색은 중복 제출하지 않는다. 실패 응답에 대해 무제한 자동 재시도나 유료 대체 검색을 하지 않는다. 원문 링크는 계속 확인할 수 있다.

## 운영 중 중단 절차

일반적인 API 작업 중단은 `server/public-api-policy.mjs`의 `publicApiPolicy.enabled`를 `false`로 바꾸고 재배포한다. 대안으로 `USED_PUBLIC_API_ENABLED=false` 환경변수를 설정한 후 해당 환경을 재배포할 수 있다. 환경변수의 `true` 값은 코드 정책의 `false`보다 우선하므로, `true` override가 설정돼 있다면 함께 해제하거나 `false`로 바꿔야 한다.

이 중단은 배포가 반영된 뒤 새 함수 작업을 막는다. 이미 진행 중인 작업과 CDN·탭 캐시의 기존 결과까지 즉시 제거하지는 않는다. 긴급하게 운영 사이트 전체의 새 접근을 제한하려면 관리자가 Vercel Deployment Protection을 모든 배포에 적용할 수 있다. 이미 브라우저에 전달된 정보는 회수되지 않는다.

중단 후에는 Vercel의 Usage와 함수 로그에서 사용량·오류 증가 원인을 확인한다. 기본 애플리케이션 로그는 제공사별 상태·결과 수와 오류 종류를 남기며, 검색어·IP를 직접 로그에 쓰지 않는다. 호스팅 플랫폼의 접근 로그 보관 범위는 별도다. 원인을 해소한 후 정책을 다시 켜고 재배포한다.

## 현재 없는 장치와 향후 변경 조건

현재 배포에 별도 WAF 레이트리밋이 적용됐다고 보장하지 않는다. 방화벽의 기존 구성을 읽어 확인하지 못한 상태에서 전체 설정을 덮어쓰지 않았다. 이 문서의 IP 제한은 서버 함수 안의 애플리케이션 제어다. 제한 응답 자체도 함수 실행과 정상 트래픽 사용량을 일부 소비한다.

추후 방화벽 구성을 확인할 수 있으면 API 두 경로에 한정한 WAF 레이트리밋 1개를 추가하는 것이 다음 보강 단계다. Hobby에는 레이트리밋 규칙 1개와 허용 요청 100만 회가 포함된다. WAF 카운터도 CDN 리전별이므로 함수 실행 리전을 서울로 지정했다고 전역 카운터가 되지는 않는다. [Vercel WAF 레이트리밋](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)

WAF에서 차단·챌린지·레이트리밋 처리한 트래픽에는 CDN Requests와 Fast Data Transfer가 부과되지 않지만, 통과한 요청은 정상 사용량에 포함된다. [WAF 사용량과 비용](https://vercel.com/docs/vercel-firewall/vercel-waf/usage-and-pricing)

Pro로 업그레이드하거나 유료 통합을 추가하면 이 문서의 무료 운영 전제가 바뀐다. Pro의 Spend Management는 확인 주기로 인해 예산을 넘은 뒤에도 수분간 사용량이 발생할 수 있으므로, 예산 설정만으로 0원 운영을 보장할 수 없다. [Spend Management](https://vercel.com/docs/spend-management)

Hobby는 비상업 개인 용도에 한정된다. 금전적 이익을 목적으로 운영하거나 광고·제휴 수익 등 상업 기능을 도입하기 전에는 요금제 적합성을 다시 확인한다. 사용자에게 무료로 제공한다는 이유만으로 Hobby 조건을 만족한다고 단정하지 않는다. [Vercel Fair Use](https://vercel.com/docs/limits/fair-use-guidelines)

## 검증 기준

- 종류·서비스가 다르면 검색·캐시 결과가 섞이지 않아야 한다.
- 잘못된 입력과 알 수 없는 파라미터는 원문 조회 전에 거부해야 한다.
- 동일 키의 동시 요청은 외부 조회 하나로 합쳐져야 한다.
- 캐시 만료·용량 상한, IP 한도, 동시 처리 제한과 중단 정책을 각각 검증한다.
- 차단·과부하 응답이 엔카 복구 조건으로 잘못 해석되지 않아야 한다.
- 상세 캐시에서 다른 매물, 취소된 응답, 오류 응답을 표시하지 않아야 한다.
- 가격·지역·정렬만 바꿀 때 검색 API를 새로 호출하지 않아야 한다.
- 운영 공개 후 인증 없는 요청으로 홈·검색·상세의 응답과 실제 원문 링크를 확인한다.

자동 검증은 `npm test`와 `npm run check`로 실행한다. 전체 테스트·배포 후 검증은 릴리스 시점의 실행 결과를 기준으로 확인한다.
